# 运行原理

## 一句话概括

函数每分钟做一次「三方对账」——**副本实际有哪些 IP**、**后端服务器组里注册了哪些 IP**、**上一轮记了哪些 IP**——然后把差异补齐。

新出现的 IP 立刻注册；消失的 IP 要连续消失若干轮才摘除。

## 为什么要"不对称"

注册和摘除的代价完全不同：

| | 做错的后果 |
|-|-|
| **多注册**一个不该注册的 IP | 健康检查会立刻把它标记为异常，不会有流量打过去。损失≈0 |
| **误摘除**一个正常的 IP | 容量瞬间少一份。副本本来就不多的时候，剩下的副本可能被打垮 |

所以策略是**激进注册、审慎摘除**：

- 发现即注册，不做任何确认；
- 消失后进入「待摘除」名单并开始计数，连续 `invocations_before_deregistration` 轮（默认 3 轮，即约 3 分钟）都不在册，才真正摘除。中途只要重新出现一次，计数清零。

## 七步流程

```
Step 1 发现副本 IP → discovery_set
Step 2 读后端服务器组当前成员 → pool_set
Step 3 读对象存储里上一轮的状态 → prev_active_set / prev_pending_dict
Step 4 待注册 = discovery_set - pool_set
Step 5 待摘除候选 = (prev_active_set - discovery_set) ∪ (pool_set - discovery_set)
对每个候选累加计数；计数 ≥ 阈值的才进入真正的摘除名单
Step 6 批量注册；批量摘除（先过熔断检查）
Step 7 状态回写对象存储
```

### Step 1：发现

`rds_api` 模式逐个查询实例，把 `private_ips` 汇总成一个集合。单个实例查询失败不会中断整轮——记一条错误日志然后跳过，剩下的副本照常处理。

`dns` 模式逐个解析域名，每个域名最多重试 `max_lookup_per_invocation` 次。

**一轮下来一个 IP 都没发现时，函数直接返回，不做任何后端变更。** 这是最重要的一道保险：发现链路整体故障（API 不可达、域名服务异常）看起来和"所有副本都没了"一模一样，此时什么都不做，远好过把后端摘空。

### Step 2：读当前成员

分页拉取后端服务器组的成员列表，取每个成员的 `address`。

这里用的是成员列表接口而不是健康检查结果——状态机关心的是"注册了没有"，不是"健康不健康"。健康与否由健康检查独立处理，两条链路互不干扰。

### Step 3：读上一轮状态

对象存储里有两个文件：

| 文件 | 内容 |
|-|-|
| `<state_prefix>/active_ip.json` | 上一轮成功注册后的活跃 IP 快照 |
| `<state_prefix>/pending_ip.json` | `{IP: 连续缺失次数}` |

首次执行时两个文件都不存在，读取返回空字典，流程正常继续。

### Step 4：待注册

```
待注册 = 本轮发现的 - 已注册的
```

没有任何延迟，直接进 Step 6 注册。

### Step 5：待摘除

候选集合来自两个方向：

```
候选 = (上一轮活跃的 - 本轮发现的) ∪ (已注册的 - 本轮发现的)
```

第一项抓的是"上一轮还在、这一轮不见了"；第二项抓的是"注册进去了但从来没被发现过"（比如手工加进去的成员）。

对候选逐个计数：

- 上一轮就在待摘除名单里 → 计数 +1；
- 第一次进入名单 → 计数置 1；
- 上一轮在名单里、本轮又被发现了 → 直接从名单移除，计数丢弃。

计数 ≥ `invocations_before_deregistration` 的，才进入真正的摘除名单。

### Step 6：写后端

**注册**：走批量接口，每批最多 200 个。同 VPC 时成员带 `subnet_cidr_id`，跨 VPC 时不带。

**摘除前先过熔断**：

```
本轮要摘的数量 / 当前已注册数量 > max_deregistration_percent% → 跳过，只告警
```

默认 50%。这一层挡的是"发现链路半瘫"这类场景——比如权限被误改导致一半副本查不到，计数会正常累加到阈值，但熔断会拦住这次摘除并留下明确告警。

摘除同样走批量接口，用 `address + 端口` 定位成员。批量接口逐条返回结果，`not found` 视为正常（说明已经被摘掉了），只记日志。

### Step 7：回写状态

- **只有注册接口调用成功，才写 `active_ip.json`。** 注册失败时不写，下一轮会重新把这些 IP 算进待注册集合，自动重试；
- `pending_ip.json` 每轮都写，保证计数连续。

## 收敛性

单轮执行不保证发现全部副本——API 可能超时，DNS 可能解析失败。但每轮都在往正确方向推进，多跑几轮必然收敛：

- 漏发现的 IP，下一轮会被发现并注册；
- 误判为缺失的 IP，计数还没到阈值就会被重新发现，计数清零；
- 注册失败的 IP，因为状态没落盘，下一轮原样重试。

## 参数怎么调

| 参数 | 默认 | 调大 | 调小 |
|-|-|-|-|
| `schedule` | `1m` | 感知变慢，函数调用次数减少 | 感知变快，调用次数线性增加 |
| `invocations_before_deregistration` | `3` | 更抗抖动，但故障副本会在后端多待一会儿 | 摘得更快，误摘风险上升 |
| `max_lookup_per_invocation` | `3` | 单次执行更容易发现全部副本，耗时增加 | 执行更快，单轮发现率下降 |
| `max_deregistration_percent` | `50` | 熔断更松，大规模缩容时不会被挡 | 熔断更严，更容易误报 |

**真正摘除一个副本所需时间 ≈ `schedule` × `invocations_before_deregistration`。** 默认配置下约 3 分钟。想更快就调小计数阈值，而不是调小调度周期——后者会线性放大调用次数。

`function_timeout` 必须小于调度周期，否则相邻两次执行会重叠。模板已经在 plan 阶段就把这条约束检查了。

## 副本状态与摘除

`rds_require_active_status` 默认 `false`：只要 云数据库 返回了实例的 `private_ips`，就算在册，不看实例状态。

这是有意的。实例重启、规格变更期间状态不是 `ACTIVE`，但 IP 还在、恢复也快，此时直接摘除反而制造抖动。真正不可用的副本会被**健康检查**先剔除流量，然后如果实例被删除，`private_ips` 自然消失，摘除计数才开始累加。

需要更严格的语义时把它设为 `true`。

## 怎么看运行情况

每次执行结束会输出一条 JSON 摘要：

```json
{
"event": "invocation_summary",
"request_id": "...",
"discovery_mode": "rds_api",
"discovered_ips": 2,
"registered": 0,
"deregistered": 0,
"deregistration_skipped": false
}
```

在 LTS 里按 `event: invocation_summary` 过滤即可看时间序列。几个值得配告警的信号：

| 信号 | 含义 |
|-|-|
| `discovered_ips` 掉到 0 | 发现链路故障，或者副本真的全没了。函数此时不做任何变更 |
| `deregistration_skipped: true` | 熔断触发，需要人工介入 |
| `registered` 长期非 0 | 注册没有生效，检查委托权限和后端服务器组类型 |

排查具体某一轮时，把日志级别调到 `DEBUG` 能看到每一步的集合运算中间结果。

## 已知边界

| 边界 | 说明 |
|-|-|
| 单条 A 记录 | `dns` 模式假设每个副本域名只解析出一个 IP。多 IP 也能工作，但会被当成多个后端 |
| IPv4 | 后端成员只处理 IPv4 |
| 单一写入方 | 后端成员应当只由本函数维护。手工加进去的成员会被当成"未被发现"，最终被摘除 |
| 无跨区域 | 副本必须在负载均衡器同区域。跨区域需要另一套方案 |
